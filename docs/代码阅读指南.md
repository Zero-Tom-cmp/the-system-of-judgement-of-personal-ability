# 人岗匹配评估系统 · 代码阅读指南

> **给谁看**：想自己读懂这套代码、然后自己画架构图的人。不需要你懂 FastAPI 或 React。
> **怎么用**：按「第 2 节」的四站路线走，一站在 10–40 分钟。**不要**从第一个文件夹往下顺着读。

---

## 一、先摆正心态：你要读的其实很少

全套代码的规模：

| 部分 | 文件数 | 总行数 |
|---|---|---|
| 后端源码（7 个 .py） | 7 | 3505 |
| 前端源码（src/ 下 34 个文件） | 34 | 2443 |
| 后端测试 | 5 | 1141 |
| **合计** | | **≈ 7000** |

看到 7000 行不要慌，因为：

- **测试（1141 行）不用读**——那是给机器跑的，画架构图完全用不上。
- **后端 7 个文件里，要精读的只有 4 个**（`main.py` 还只需读它的"目录"）。
- **前端 34 个文件里，要精读的只有 3 个**，剩下 31 个是"同一套写法换了个数据表"，读懂一个就等于读懂全部。

**真正需要逐行看的，大约是 1400 行。**

还有一批**完全不用打开**的文件，见第 7 节——先看那一节，能帮你省掉一大半困惑。

## 三、阅读路线：四站，从骨架到器官

顺序是有讲究的：**先看清系统长什么样，再看它有哪些能力，再看数据长什么样，最后才碰算法。**
反过来读（一上来啃 main.py）是绝大多数人放弃的原因。

### 第 1 站 · 看系统长什么样
**读 1 个文件：`frontend/src/App.jsx`（98 行，全读）**

这是整个系统的**目录**。98 行读完全部，你立刻知道：

- 系统一共几个页面、网址分别是什么
- 哪些页面是管理员的，哪些是学生的

**要看的地方**：第 65–93 行的 `<Routes>` 块。

```
/                → 登录页（谁都能进）
/student         → 学生端   （第 67 行，PrivateRoute allowedRole="student"）
  ├─ 首页/课程/竞赛/实习/项目/培养方案/能力评估/岗位匹配/简历
/admin           → 管理员端 （第 78 行，PrivateRoute allowedRole="admin"）
  ├─ 数据总览（首页）
  ├─ student/:studentId → 学生详情（8 个页签，第 80–89 行）
  ├─ import  批量导入
  ├─ logs    操作日志   （第 91 行 —— 注意：路由有，但左侧菜单里没入口）
  └─ rules   规则配置
```

**顺带读掉第 53–59 行的 `PrivateRoute`**，它就是架构图里「认证权限中心 · 前端路由守卫」那格：

```jsx
const token = localStorage.getItem("token");
const role  = localStorage.getItem("role");
if (!token) return <Navigate to="/" replace />;          // 没登录 → 踢回登录页
if (allowedRole && role !== allowedRole) ...             // 角色不对 → 也踢回去
```

> **本站在架构图上的产出**：「角色与权限设计」那一部分。管理员和学生的功能差异，从这两个路由分支就能直接画出来。

**读 1 个文件：`backend/main.py`（1327 行，但只读「目录」）**

⚠️ **千万不要从头逐行读 1327 行。** 这个文件是一张「接口清单」，1327 行里绝大部分是重复的样板。

payload = verify_token(request.headers.get("Authorization", "").replace("Bearer ", ""))

### 第 4 站 · 看核心算法
**读 3 个文件，按这个顺序：`evaluation.py` → `match_score.py` → `ability_score.py`**

这是全系统最有价值的部分，也是架构图上两个核心模块的颜色来源。顺序是**从大到小**：先看整体怎么算，再看公式细节。

#### 4.1 `backend/evaluation.py`（459 行）—— 能力评估中心

**它解决的问题**：把学生的 5 类原始数据，换算成 0–100 的能力分。

**读法**：先读开头的模块 docstring（Python 文件开头的三引号说明），再看这几个函数：

| 函数 | 干什么 |
|---|---|
| `evaluate_student_abilities()` | **主入口**。总装线，调下面 5 个 |
| `_eval_courses()` | 课程贡献 |
| `_eval_competitions()` | 竞赛贡献 |
| `_eval_internships()` | 实习贡献 |
| `_eval_projects()` | 项目贡献 |
| `_eval_english_cert()` | 英语证书贡献 |
| `_get_improvement_suggestion()` | 生成提升建议 |

**这 5 个 `_eval_xxx` 的结构几乎一模一样**，读懂一个（建议读 `_eval_courses`）就知道其余 4 个在干嘛。它们的产出是一份「贡献明细」，最后汇总归一化成百分制。

这就是架构图上「能力评估中心 · 得分溯源明细」那一格的来历：算分的同时留下了「哪门课贡献了多少分」。

#### 4.2 `backend/match_score.py`（386 行）—— 岗位匹配中心

**它解决的问题**：能力分拿到了，怎么跟岗位要求比？

**核心公式**（文件 docstring 里有，第 1 站说的"异常完善的中文文档"就是指这个）：

```
单维度匹配度   mᵢ = 1 − |sᵢ − rᵢ|      sᵢ = 学生能力分，rᵢ = 岗位要求分
综合匹配度     D  = Σ eᵢ · mᵢ          eᵢ = 该维度权重
百分制         Score = 100 · D
```

**读法**：先读文件开头 docstring，然后按顺序看这几个函数：

| 函数 | 干什么 |
|---|---|
| `certain_match()` / `fuzzy_match()` | 算单个维度的 mᵢ |
| `match_dimension()` | 算一整个维度（含权重处理） |
| `combine_matches()` | 汇总成 D |
| `match_job()` | **主入口**，算一个岗位的完整匹配结果 |
| `apply_gates()` | 硬性门槛（一票否决），默认关闭 |

**这个文件里最需要理解的一个设计**：文档里反复强调的
> 本模型衡量的是**匹配**，不是**优秀**——超出岗位要求同样算偏离、同样扣分。

这就是为什么界面上会有橙色提示"能力已超过岗位要求"。这条设计会直接体现在你的架构图上（MATCH 模块的说明文字）。

#### 4.3 `backend/ability_score.py`（93 行）—— 归一化

**最短也最简单，93 行，建议全读。** 它只做一件事：把任意尺度的原始分压到 0–1。

```python
DEFAULT_REFERENCE_RAW = 40.0
def normalize_ability(raw, ...):
    return clamp01(value / ref)          # 除以参考上限 40，再夹到 [0,1]
```

读懂它，你就明白了架构图里「**能力分只表达强弱，不乘权重**——权重统一交给匹配公式」这句话。**一个概念只出现一次**，这是这套代码里最干净的一处设计。

## 四、把前后端接起来：追踪一个请求

四站读完，你手里有了「前端页面」和「后端接口」两张清单，但它们是分开的。**架构图最关键的那条"数据流"箭头，要靠这一步接上。**

**示例：学生点开「岗位匹配」页面，系统做了什么？**

| 步 | 位置 | 发生了什么 |
|---|---|---|
| 1 | `pages/student/JobMatchPage.jsx`（22 行） | 页面加载，调 API |
| 2 | `src/api.js` | axios 拦截器自动加上 `Authorization: Bearer <token>` |
| 3 | → `/api/student/2021004/job-match` | 前端带 token 发起请求 |
| 4 | `backend/main.py:281` `get_job_match()` | **鉴权**：token 里的 id ≠ URL 里的 id 且非管理员 → 403 |
| 5 | `backend/main.py` → `match_jobs(cursor, student_id)` | 转交业务层 |
| 6 | `backend/evaluation.py` `match_jobs()` | 先算出该生的能力分 sᵢ |
| 7 | `backend/match_score.py` `match_job()` | 拿 sᵢ 和岗位要求 rᵢ、权重 eᵢ 算匹配度 D |
| 8 | `backend/database.py` | 读 `job_ability_profile`（岗位要求）、`ability_config`（权重） |
| 9 | 原路返回 JSON | 前端渲染匹配分、雷达图、差距、建议 |

**这条链就是架构图主干上的四个色块**：DATA → EVAL → MATCH，外加 AUTH 网关在最前面。

> **建议你亲手做一次**：在 `main.py` 里找到 `get_job_match`，然后把 `match_jobs` 这个词选中，按 `Ctrl + Shift + F` 搜，看它定义在哪、被谁调用。这个动作叫「**跳转追踪**」，是读代码的核心技能。追通一条链，比读十个文件有用。

**再自己追两条**（都更简单，用来巩固）：
- 学生看简历：`ResumePage.jsx` → `/api/student/{id}/resume` → `main.py:294` → `resume.py build_resume_payload()`
- 管理员导入 Excel：`ImportPage.jsx` → `/api/admin/import/all` → `main.py:1001` → `database.py` 各表

## 六、读一个函数的通用方法（三问）

任何一段代码卡住时，问自己三个问题：

1. **它吃什么？**（参数是什么）
2. **它吐什么？**（返回什么）
3. **谁在调它？**（选中函数名 → `Ctrl + Shift + F`）

三个问题答完，这个函数就不用看了。**画架构图不需要看懂每一行实现，只需要知道「谁给谁什么东西」**——那正是箭头上的标签。

另外，**先读中文文档字符串**。这套代码的每个模块开头都有详尽的中文说明，作者已经把「这个文件解决什么问题、公式是什么、为什么这么设计」写清楚了。**读 20 行 docstring 常常胜过读 200 行代码。**

**顺带说明两个你可能会撞上的疑问**：

- `ability.db`（0 字节）是残留的空文件，系统实际用的是 `person_job_match.db`。
- 前端里有一批只有 20–70 行的文件，**不是因为功能简单，而是因为它们的活都交给了 `components/` 里的公共组件**（`DataTable`、`AbilityRadar`、`ScoreExplain`、`JobMatchPanel`）。所以真正要读的前端文件是那 5 个组件，不是 35 个页面。

## 八、读完之后：架构图的五个问题你现在答得出来了吗

回头看你要画的图，它需要回答的问题就这五个，而它们正好对应四站阅读：

| 架构图要回答的 | 在哪读到 |
|---|---|
| ① 系统分几块？每块叫什么？ | 第 2 站的接口分类表 + 第 5 节对照表 → **8 个模块** |
